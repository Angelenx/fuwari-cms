# Fuwari 风个人博客 CMS · 初版开发思路

> 目标读者：自己动手实现  
> 日期：2026-09-17  
> 约束：**前台观感对齐 [Fuwari](https://github.com/saicaca/fuwari)（MIT）**；**正文进 Cloudflare D1**；有独立后台；图可进 R2；AI 先留接口后做。  
> 本文只谈思路与边界，不包含可运行代码。

---

## 0. 要解决什么问题

| 想要 | 现成方案的缺口 |
|------|----------------|
| 好看（偏 Fuwari） | 乔木等 CMS 功能强，默认观感不对味 |
| 后台写稿 + 真数据库 | Fuwari 本身是纯静态 Markdown，无 D1、无后台 |
| 跑在 Cloudflare | 需要 Workers + D1（+ 可选 R2 / Workers AI） |

结论：**用 Fuwari 当「皮肤与信息架构」；自己做「内容层 + 管理端」**。  
不是改乔木换皮，也不是继续用 Git 当数据库。

---

## 1. 产品一句话

**单仓库、同一 Worker：公开站长得像 Fuwari；管理员登录后台用 Markdown 写文章；文章存在 D1；发布后前台 SSR 直接读库。**

---

## 2. 推荐技术选型（初版只认这一套）

| 层 | 选型 | 为什么 |
|----|------|--------|
| 前台 | Astro + Tailwind + 少量 Svelte（跟 Fuwari 对齐） | 直接复用主题组件/样式，观感成本最低 |
| 部署 | `@astrojs/cloudflare`，`output: 'server'` → **Workers** | 改库即可见，不必每次发文重建静态站；原生绑 D1/R2 |
| API | 同进程 **Hono**，路由前缀 `/api/*` | 轻、和 CF 契合，后台与公开接口分开清晰 |
| 数据库 | **D1** | 已定；个人博客体量足够 |
| 媒体 | **R2**（可第二期） | 封面/插图；元数据仍进 D1 |
| 后台 UI | 同站 `/admin/*`（Astro 页） | 同域 Cookie、一次部署；初版不必另开 SPA |
| 鉴权 | **单管理员密码 + HttpOnly Session Cookie** | 一人用；比 Cloudflare Access 落地快 |
| 正文格式 | Markdown 存 D1，服务端渲染 HTML | 对齐 Fuwari 的 Markdown 样式链 |
| AI | Workers AI **只留 stub** | 不挡发文主路径 |

**初版明确不选**

- Next.js / OpenNext（和 Fuwari 主题复用差，容易做成第二个乔木）
- 正文仍走 Content Collections / Git（那就不是「文章进 D1」）
- 多用户、复杂权限、评论系统（可后置）

**可选旁路（若不想自建）**  
社区里有「Fuwari 风 + D1 后台」的成品（如 Flare Stack Blog），但是 GPL、AI 偏审核而非写作。你已倾向自建，下文按自建写；成品只作对照，不作为本方案依赖。

## 3. 逻辑架构

```
浏览器
  ├─ 公开站  /  /posts/:slug  /archive  /tags/...
  │     Astro SSR  →  查 D1（仅 published）  →  Fuwari 布局渲染
  │                  →  封面/图 URL（R2 或外链）
  │
  ├─ 管理端  /admin/*
  │     登录页 + 文章列表/新建/编辑（需有效 session）
  │
  └─ API     /api/*
        Hono
          ├─ /auth/login|logout|me
          ├─ /admin/posts  CRUD（需登录）
          ├─ /admin/media  上传 R2（可选）
          └─ /admin/ai/*   stub → 501（三期）

同一 Cloudflare Worker
  bindings: DB(D1), MEDIA(R2 可选), SESSION_SECRET
  （三期再绑 AI）
```

核心变化相对原版 Fuwari：

| 原 Fuwari | 本方案 |
|-----------|--------|
| `src/content/posts/*.md` | D1 `posts` 表，Markdown 文本列 |
| `getCollection` / 构建期分页 | 运行时查库 + SSR |
| `pnpm new-post` 写文件 | 后台表单 → API → D1 |

## 4. 数据模型思路（D1）

够用即可，避免一开始过度设计。

**`users`**（初版一行管理员即可）  
`id`, `username`, `password_hash`, `created_at`

**`sessions`**  
`id`（随机 token）, `user_id`, `expires_at`, `created_at`

**`posts`**  
`id`, `slug`(unique), `title`, `description`,  
`body_md`, `body_html`（可缓存，写入/更新时生成）,  
`cover_url`, `status`(`draft`|`published`),  
`category`, `published_at`, `created_at`, `updated_at`,  
`word_count`, `reading_minutes`（给 PostCard 用，避免每次现场算）

**`tags` + `post_tags`**  
多对多；侧栏 Tags、标签页靠这两张表。

**`media`**（R2 上线后再用）  
`id`, `key`, `url`, `mime`, `size`, `created_at`

索引建议：`posts(status, published_at DESC)`、`posts(slug)`、`sessions(expires_at)`。

密码：Workers 上初版用 **PBKDF2-SHA256**（Web Crypto）即可；库内只存 hash。`SESSION_SECRET` 放 secrets，不要进明文 vars。

## 5. API 纲要（思路级）

### 公开（可不登录；或只给 SSR 用、不对外暴露细节）

- 列表/详情也可以 **只在 Astro 服务端直连 D1**，不一定非走 HTTP。  
- 若要给未来小程序/友链用，再补：
  - `GET /api/posts`（仅 `published`，分页）
  - `GET /api/posts/:slug`

### 鉴权

- `POST /api/auth/login` `{ username, password }` → Set-Cookie  
- `POST /api/auth/logout`  
- `GET /api/auth/me`

Cookie 建议：`HttpOnly; Secure; SameSite=Lax; Path=/`

### 管理（必须登录）

- `GET/POST /api/admin/posts`  
- `GET/PUT/DELETE /api/admin/posts/:id`  
- `POST /api/admin/media`（multipart → R2）  
- `POST /api/admin/ai/suggest-title` 等 → 初版直接 `501`

约定：`draft` 永不出现在公开查询里。

## 6. 前台怎么「仍然像 Fuwari」

**策略：复制主题壳，替换内容源。**

1. 从 Fuwari 带走：Layout、Navbar、Footer、Sidebar、PostCard、Markdown 样式、主题变量、i18n、图标与过渡动画相关配置。  
2. 改掉：所有 `getCollection` / Content Collections；`PostCard` 里依赖 `entry.render()` 的逻辑，改成传入已算好的 excerpt / 字数 / 阅读时间。  
3. 封面：相对路径改为 **绝对 URL**（R2 或外链）。  
4. `/admin` 路径关掉页面切换动画（若用了 Swup），避免和后台打架。  
5. Pagefind 全文搜索初版可隐藏；二期用 D1 FTS5 或再接搜索。

许可：Fuwari 为 **MIT**，复用主题合法，仓库需保留归属声明（README / NOTICE）。

## 7. 管理端初版交互（别做成乔木）

目标是「能稳定发文」，不是「全能 CMS」。

- 登录页  
- 文章列表（状态、时间、快捷发布/撤回草稿）  
- 编辑页：标题 / slug / 摘要 / 标签 / 封面 URL / 状态 + **Markdown 大文本框** + 简易预览  
- 暂不引入重型可视化编辑器（可列为二期）

这样后台可以很素；**好看留给前台 Fuwari**。

---

## 8. 分期（建议按这个顺序想，而不是一次做完）

### 一期（MVP：能登录、能发、前台像 Fuwari）

1. 定仓结构与 Cloudflare 绑定（Worker + D1）  
2. 迁入 Fuwari 主题，先保证布局/样式在 SSR 下可用  
3. 落地表结构 + 种子管理员  
4. 服务端读库：首页分页、详情、标签、归档  
5. 鉴权 + `/admin` 最小 CRUD  
6. README 写明基于 Fuwari（MIT）

**一期不做：** 真 AI、评论、搜索、多作者、复杂编辑器。

### 二期

- R2 上传与媒体库  
- 搜索（D1 FTS5）  
- RSS / sitemap / OG 完善  
- 可选：Cloudflare Access 替换自建密码

### 三期（有余力再想）

- Workers AI：标题/摘要/标签建议  
- 更舒服的编辑器、阅读统计、友链/说说等扩展类型

---

## 9. 实现时的推荐顺序（仍是思路，不是排期承诺）

```
主题可运行（SSR）
    → D1 读写替换 Content Collections
        → 登录与 session
            → 后台 CRUD
                →（可选）R2
                    →（更后）AI stub / 真调用
```

每一步都应该能单独验收：例如「只有只读前台 + 手写 SQL 插入一篇」也可以先证明数据通路。

---

## 10. 风险与坑（提前知道）

1. **Fuwari 默认偏静态生成**；改 SSR 后，构建期插件（如 Pagefind）和部分假设会裂，要按「运行时数据」重想。  
2. **Markdown 插件链**（代码高亮、提示块、GitHub card）要在「写入时渲染」或「读取时渲染」里二选一；建议写入时缓存 `body_html`，前台轻。  
3. **缓存**：SSR + D1 默认已够快；上 CDN 缓存后要注意「发文后要让公开页失效」。初版可以不做边缘缓存。  
4. **本地开发**：需要 wrangler / adapter 能注入 D1；文档里把 `wrangler d1 execute` 迁移写清楚。  
5. **安全**：登录限速、slug 唯一、管理 API 全鉴权、上传类型白名单（上 R2 时）。

## 11. 你需要先拍板的少数决策

| 项 | 建议默认 | 备选 |
|----|----------|------|
| 鉴权 | 密码 + Session Cookie | Cloudflare Access |
| 编辑器 | Markdown textarea + 预览 | 二期再上 CodeMirror / TipTap |
| 图片 | 一期可先外链；二期 R2 | 一期就上 R2 |
| AI | 三期再做 | 若你强依赖写作 AI，可提前 |

其余（单仓库、Astro+Fuwari、D1、同站 `/admin`）按上文默认即可，减少摇摆。

---

## 12. 成功标准（初版什么叫「做成了」）

- 管理员能登录后台，创建/编辑/发布/撤回草稿  
- 公开站首页、文章页、标签/归档 **看起来就是 Fuwari 那路**  
- 刷新公开站能读到刚发布的 D1 内容，无需重新 `git push` 文章文件  
- 草稿绝对不会出现在公开列表  
- 仓库有清晰归属：主题来自 Fuwari（MIT）

## 附：和「直接用成品」怎么选

| 路径 | 适合 |
|------|------|
| **按本文自建** | 要完全控观感与数据模型；愿意写后台 |

| Flare Stack 等 GPL 成品 | 想尽快有「好看 + D1 后台」，能接受许可证与功能取舍 |

你当前选择是 **自建**；本文即该路径的初版开发思路。
